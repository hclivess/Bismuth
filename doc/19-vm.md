# doc/19 — Decentralized-apps VM (smart contracts)

The on-chain, **post-fork** smart-contract layer. This is the complete map of what exists, what is
tested, and what is still missing — so nothing is assumed done that isn't.

Everything here is **inert until hf2 activates** and behind the `vm` config flag (default **off**; on for
regnet tests). It adds **no behaviour to the current chain**.

## How it fits together

```
vm: transaction (consensus-ordered, signed, in a block)
        │  digest, ONLY when block_height >= node.fork_height  (digest.py)
        ▼
vm_engine.apply_block_rows ──> per tx: parse vm:deploy / vm:call
        │                               dispatch on the contract's engine tag
        ▼
   execution engine            ┌─ bismuth_vm.py     (compact EVM-style bytecode)   ENGINE 0
   (pluggable)                 └─ bismuth_riscv.py  (RV32I RISC-V interpreter)      ENGINE 1
        │  reads/writes
        ▼
   vm_state.py  (LMDB: code + storage)  ──>  vm_state.state_root()  ──> node.vm_state_root
```

## Value custody — the design (the one consensus piece still to wire, carefully)

The VM-level mechanism (TRANSFER, balance-checked) is done. The consensus value-flow — contracts actually
moving BIS — is **deliberately not rushed**, because the obvious approach (contract balance = its ledger
balance) is **not rollback-deterministic**: on a reorg the state is rebuilt by re-executing the `vm:` txs,
but a contract's *historical* spendable balance can't be reproduced from the rolled-back ledger (the
ledger only holds the final, rolled-back balances). A TRANSFER that succeeded originally would fail on
replay, diverging the storage/root. Getting this wrong is a **money bug** — worse than the gap.

**The correct, rollback-deterministic design:** hold the contract balance **in `vm_state`** (committed to
the state root), not the ledger.
  - **Deposit:** a `vm:call` carrying value debits the sender's ledger to a fixed `vm` sink and credits the
    contract's `vm_state` balance (double-entry; the sink's ledger balance mirrors the sum of all contract
    balances).
  - **Withdraw:** TRANSFER debits the contract's `vm_state` balance and credits the recipient's ledger from
    the sink.
  - **Replay:** the `vm_state` balance is rebuilt *deterministically* by re-executing the `vm:` txs
    (deposits add, transfers subtract), so `self_balance` is reproducible at every point → the rollback
    rebuild matches. The state root already covers `vm_state`, so the balances are consensus-committed.

This is straightforward but money-critical: it needs the `vm_state` balance map, the deposit/withdraw
ledger rows, in-block accounting (no double-spend across calls), and a thorough HTLC-with-value +
reorg-determinism test suite before it touches consensus.

## Layer model (important)

Execution is **main-layer** (every full node runs it; `vm:` txs are consensus-ordered and final), and the
state root is now **consensus-ENFORCED**: post-fork the miner commits the pre-state root in the coinbase
(after the hf2 signal, PoW-hashed like the rest of the nonce) and the digester **rejects** a block whose
committed root disagrees with its own. So a non-determinism bug is a **caught block-rejection, not a
silent divergence** — main-layer execution *plus* the hash-anchored integrity an L2 hash-commit gives,
with no separate layer or sequencer. See doc/17 for the trade-off.
