# doc/19 — Decentralized-apps VM (smart contracts)

The on-chain, **post-fork** smart-contract layer. This is the complete map of what exists, what is
tested, and what is still missing — so nothing is assumed done that isn't.

Everything here is **inert until hf2 activates** and behind the `vm` config flag (default **off**; on for
regnet tests). It adds **no behaviour to the current chain**.

## How it fits together

```
vm: transaction (consensus-ordered, signed, in a block)
        │  digest, ONLY when block_height >= node.fork_height  (digest.py)
        ▼
vm_engine.apply_block_rows ──> per tx: parse vm:deploy / vm:call ; value custody deposit/withdraw
        │
        ▼
   bismuth_riscv.py   the single execution engine: deterministic RV32I RISC-V interpreter
        │             (ALU / branches / load-store / JAL(R) / LUI / AUIPC, gas-metered, ECALL host ABI)
        │  reads/writes
        ▼
   vm_state.py  (LMDB: code + storage + custody balances)  ──>  state_root()  ──> node.vm_state_root
```

Why RISC-V and not a bespoke bytecode: it's a real, frozen, widely-implemented ISA with mature C/Rust
toolchains, inherently deterministic in its base integer set — the direction Ethereum itself is taking
("RISC-V over the EVM"). One engine, no dispatch.

## Value custody — how it works (DONE)

Contracts move real BIS, and a reorg can't corrupt it. The obvious approach (contract balance = its ledger
balance) is **not rollback-deterministic**: on a reorg the state is rebuilt by re-executing the `vm:` txs,
but a contract's *historical* spendable balance can't be reproduced from the rolled-back ledger, so a
TRANSFER that succeeded originally would fail on replay and diverge the root. The fix — implemented — holds
the contract balance **in `vm_state`** (committed to the state root), not the ledger:
  - **Deposit:** a `vm:call` sent to `VM_SINK` (a keyless 56-hex address) debits the sender's ledger to the
    sink and credits the called contract's `vm_state` balance. The sink's ledger balance mirrors the sum of
    all contract balances (double-entry) → the BIS supply stays exact.
  - **Withdraw:** a TRANSFER inside the contract debits its `vm_state` balance; the digester settles a
    `vm_payout` — a negative-height ledger row FROM the sink TO the recipient (the reward-mirror pattern).
  - **Replay:** re-executing the `vm:` txs rebuilds the `vm_state` balances exactly (deposits add, transfers
    subtract), so `self_balance` is reproducible at every height → the rollback rebuild matches, and the
    state root (which now covers balances) confirms it.

Tested end-to-end on regnet (`test_vm_value.py`): BIS funded through custody is released to a fresh address
that receives it; and after a withdraw is REORGed away, the custody balance and the state root return to
their exact pre-withdraw values — the determinism property, asserted.

## Layer model (important)

Execution is **main-layer** (every full node runs it; `vm:` txs are consensus-ordered and final), and the
state root is now **consensus-ENFORCED**: post-fork the miner commits the pre-state root in the coinbase
and the digester **rejects** a block whose
committed root disagrees with its own — *or omits it entirely* (the root is mandatory post-fork, so a
miner can't dodge the check by leaving it out). The commitment is `"vmsr"<root>`; post-fork it is carried
in the coinbase **`public_key` slot** (with the optional `hf2` signal), not the openfield, and stays
committed to the block-hash pre-image (→ **doc/41** — previously the root, nonce and signal were all
packed into the openfield). On mainnet the coinbase is built by the (external) miner,
so upgraded miners read the current root from `/api/vm/contracts` and embed it, exactly like the hf2
signal; the regnet block generator does this automatically. So a non-determinism bug is a **caught
block-rejection, not a silent divergence** — main-layer execution *plus* the hash-anchored integrity an L2 hash-commit gives,
with no separate layer or sequencer. See doc/17 for the trade-off.

## Contract flexibility — CALL / DELEGATECALL / SETCODE / SELFDESTRUCT (issue #384, SHIPPED)

The VM now has the four primitives that make contracts composable and upgradeable. They are **additive**
and **post-fork-only** with the rest of the VM (see *Fork gating* below), so a deployer **opts in** by using
them — a contract that uses none of them is exactly as immutable and isolated as before. The full syscall
set is now `SSTORE / SLOAD / CALLER / CALLVALUE / NUMBER / SHA256 / TRANSFER / CALL / DELEGATECALL /
SETCODE / SELFDESTRUCT / ADDRESS / CALLER_FULL` (+ `HALT` / `RETURN`). See **doc/44 — writing contracts** for the
complete ABI, the storage-layout discipline, the security guardrails, and worked examples; this section is
the consensus-level summary.

How they work, and the one invariant they all keep — **value custody stays exact and rollback-deterministic**:

* **`SYS_CALL`** (`9`) — call another contract. The callee runs in its **own** storage + custody; attached
  value moves caller→callee *inside* `vm_state` (no ledger payout — the custody sink total is unchanged);
  the callee's RETURN word is copied back; **an inner revert rolls back only the inner frame** and the
  caller decides what to do with the `0` it gets back.
* **`SYS_DELEGATECALL`** (`10`) — run another contract's **code** in the **caller's own** storage + custody
  + identity (`CALLER` and `CALLVALUE` are preserved; no value moves). This is the single primitive a
  *proxy* needs: a thin contract at a fixed address holds the storage and an `impl_addr` and delegatecalls
  into the implementation, so you "upgrade" by an owner-gated write of a new `impl_addr` — **the address,
  storage and custody stay; only the logic moves**. Demo: `contracts/upgradeable.py` (+ `test_vm_upgrade.py`
  upgrades it live on-chain).
* **`SYS_SETCODE`** (`11`) — a contract replaces its **own** bytecode in place (the simplest upgrade: no
  proxy, no extra contract). The new code is effective on the **next** call (the current frame finishes on
  the old code). A contract can only set *its own* code, never another's; gate it with an owner check.
* **`SYS_SELFDESTRUCT`** (`12`) — pays the contract's remaining custody to a beneficiary (a normal payout)
  and deletes its code + storage. Addresses are content-derived (unique per deploy tx) so a destroyed
  address can never be *resurrected* by a later deploy.
* **`SYS_ADDRESS`** (`13`) — a contract reads its own 28-byte address (needed for composition / passing its
  identity to a peer).

**The host model.** A single top-level `vm:call` (and every contract it CALLs/DELEGATECALLs) executes
against one journaled `vm_engine.Host`: an in-memory working set seeded lazily from `vm_state`. Nested calls
take a `checkpoint()` and `revert()` so an inner failure is isolated; on top-level success the Host
`flush()`es the whole working set to `vm_state` (storage, balances, SETCODE code, SELFDESTRUCT deletions) and
the external payouts settle from the sink; on top-level revert the Host is dropped and any attached deposit
is refunded. Storage is keyed by contract address and shared **live** across frames, so re-entrancy behaves
exactly as on the EVM — and the same well-known hazards apply (see doc/44 §Security). Calls are gas-shared
(the whole call-tree spends one `GAS_LIMIT` budget) and depth-capped at `MAX_CALL_DEPTH = 16` (the cap fires
before any Python recursion limit, so it is the consensus constant, never a platform `RecursionError`).

**Determinism & rollback.** Every new op is a pure function of on-chain data; `state_root` already covers
code + storage + balances; the reorg rebuild re-executes the same `vm:` txs in `(block_height, rowid)` order,
so a SETCODE/SELFDESTRUCT/CALL sequence reproduces the identical final state and root on replay
(`test_vm_flex.py::test_state_root_deterministic_across_replay`).

### Superseding a contract is still available
Even without upgradeability you can deploy a **v2** at a new address and migrate state/balances to it (the
old contract keeps running, frozen). Upgradeability (DELEGATECALL proxy or SETCODE) is the *in-place*
alternative — choose per contract.

### Demo: raffle (commit-reveal lottery)
`contracts/raffle.py` — anyone ENTERs by sending BIS (one ticket per call, recorded in order); the admin
DRAWs by revealing a seed whose `SHA256` was committed at deploy (the contract verifies the reveal, then
picks the winning ticket = `hash_word0 mod num_tickets`); the single winner CLAIMs the whole pot to an
address they supply, proven by `SYS_CALLER`. Showcases `SYS_SHA256` + value custody. Fairness is
**demo-grade**: the winning index is fixed by the committed hash, so a production raffle needs post-entry
entropy (a future block hash / VRF) — documented in the module and out of scope here. Tests:
`tests/test_vm_raffle.py` (9 offline adversarial cases driving the bytecode directly — non-admin draw,
wrong seed, double draw, enter-after-draw, non-winner/double claim, deterministic selection — plus a live
regnet deploy→enter→draw→claim lifecycle). UI: `web/raffle/` (`relay.py` + `index.html`), mirroring the
prediction-market relay (the relay generates the secret seed at deploy and reveals it at draw).

## Fork gating — the flexibility ops fold into hf2 (no separate fork)

The whole VM is **inert until hf2 activates** and hf2 has **not** activated on mainnet (`fork.py`; no
`fork_lockin-*.json`), so **no contracts exist on mainnet yet**. The new ops are therefore purely additive
to a not-yet-live subsystem — there is no deployed bytecode whose behaviour they could change — so they ride
the **same hf2 activation** as the rest of the VM rather than needing their own fork signal. The digester
gate is unchanged: `vm:` txs (and thus every op) run only when `block_height >= node.fork_height` with the
`vm` config flag on (`digest.py`; default off, on for regnet). If hf2 were already live with contracts
deployed, these would instead need a fresh signal — that is the *only* reason an additive VM change would; it
does not apply here. Earlier drafts of this doc assumed a separate signal would always be required; that was
written before confirming hf2 is still pre-activation.
